# Code Review

Resolve all `scripts/` paths relative to this skill's base directory.

Prerequisites: `uv` (for running the render script) and `gh` (for PR mode).

Step 1: Parse arguments
Step 2: Pre-flight (eligibility, diff, files, conventions)
Step 3: Review (all categories)
Step 4: Self-review + confidence
Step 5: Output

Local mode: review uncommitted changes.
PR mode: review a pull request.
Branch mode: review changes between a branch and HEAD.

---

## Step 1 — Parse Arguments

Parse `$ARGUMENTS`:
- Extract `--threshold N` if present → save as THRESHOLD (default 75)
- Remainder after stripping threshold flag:
  - Empty → **local mode** (review uncommitted changes)
  - Starts with `over` → if no branch name follows, ask the user which branch to compare against → **branch mode** (review changes between branch and HEAD)
  - Number or GitHub URL → **PR mode** (review pull request)
  - Anything else → stop and output:
    "Unrecognized argument: '<value>'. Usage: /code-review [<PR-number> | <PR-URL> | over <branch>] [--threshold N]"

---

## Step 2 — Pre-flight

### 2a — Eligibility Gate (PR mode only)

Skip in local mode and branch mode.

```bash
gh pr view <PR> --json state,isDraft,number,headRefOid,url,title,body,baseRefName,headRefName,additions,deletions,changedFiles,author
```

Reject if: `state` is CLOSED or MERGED, `isDraft` is true, or PR is trivial. Print reason and stop.

A PR is trivial if it only renames/moves files without content changes, or only modifies version strings in package manifests (`package.json`, `pyproject.toml`, `Cargo.toml`, etc.).

Save all returned fields for later use (PR comment permalinks, re-eligibility check).

### 2b — Gather Diff

**Local mode:**
```bash
git diff          # unstaged
git diff --cached # staged
```
Concatenate both outputs.

**Branch mode:**
```bash
git rev-parse --verify <branch>
```
If this fails, stop and output: "Branch '<branch>' not found."
```bash
git diff <branch>...HEAD
```

**PR mode:**
```bash
gh pr diff <number>
```

**Empty diff guard:** if diff is empty (all modes), skip Steps 3 and 4; go directly to Step 5 with an empty findings list.

### 2c — Read File Contents

Skip deleted files (removed entirely by the diff) — only additions and modifications have content to review.

Before reading file contents, filter out generated/vendored files in two layers:

**Layer 1 — Static skip list (always skip, no exceptions):**
- Lock files: `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Pipfile.lock`, `poetry.lock`, `uv.lock`, `Gemfile.lock`, `composer.lock`, `Cargo.lock`, `go.sum`
- Codegen: `*.generated.*`, `*.g.dart`, `*.pb.go`, `*.pb.ts`
- Vendor: `vendor/**`, `node_modules/**`
- Minified: `*.min.js`, `*.min.css`

**Layer 2 — Header detection (first 3 lines only):**
After static filtering, check the first 3 lines of each remaining changed file for generation markers: `@generated`, `Code generated`, `DO NOT EDIT`, `auto-generated by`. If any marker is found → skip the file.

Read changed files that survive both layers:

- **Binary files** (images, compiled output, `.wasm`, `.so`, `.dll`, `.pyc`, or files where the Read tool returns binary data): skip entirely.
- **Files ≤500 lines**: read in full.
- **Files >500 lines with ≤3 changed hunks**: read in full — partial read not worth the context loss for few changes.
- **Files >500 lines with >3 changed hunks**: do not read the file. Instead use `git diff -U75 <file>` for a context-enriched diff (75 lines surrounding each hunk).

### 2d — Discover Conventions

Probe repo root + every directory in each changed file's path (up to repo root, never above) for:
- `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `.clinerules`, `.windsurfrules`

Read all discovered convention files (cap: 10 files max). If more exist, prioritize directories containing changed files first, then repo root.

Do not merge or resolve contradictions between files. In Step 3, enforce rules from all files. For each convention finding, cite the deepest file that contains the rule as `rule_source`.

---

## Step 3 — Review

Review the diff for all categories simultaneously. Use chain-of-thought reasoning to analyze each changed file.

### What to look for

**Correctness** (`correctness`):
- Logic errors, off-by-one, null/undefined dereferences, unhandled edge cases
- Race conditions, deadlocks, incorrect concurrency patterns
- Async correctness (missing await, unhandled promise rejections)

**Resource management** (`resource`):
- Unclosed connections, leaked file handles, missing cleanup

**Security** (`security`):
- SQL injection, XSS, path traversal, SSRF, open redirects
- Hardcoded secrets, credentials, API keys in source
- eval/exec on user input, command injection, template injection
- Auth bypass, missing authorization checks, insecure deserialization
- Sensitive data exposure: PII in logs, stack traces or internal details in error responses, sensitive fields returned in API responses
- Insecure cryptographic usage, weak randomness for security purposes
- Focus on exploitability — skip theoretical issues without realistic attack vectors

**Convention compliance** (`convention`):
- Extract every rule from the discovered convention files
- Check the diff for violations of those rules
- Every convention finding MUST cite the exact rule text and source file
- Do NOT invent rules — only enforce what is literally written
- If no convention files were found, skip this category entirely

### Rules (hard constraints)

- ONLY flag lines introduced or modified by the diff (lines with `+` prefix)
- Do NOT flag pre-existing issues
- Do NOT flag issues a linter, type checker, or formatter would catch
- Do NOT flag pedantic nitpicks a senior dev would ignore
- Zero style/formatting comments
- Skip lines containing suppression markers: `# noqa`, `// nolint`, `@SuppressWarnings`, `// eslint-disable`, `# type: ignore`, `/* istanbul ignore */`, `// NOLINT`

### Finding format

Collect findings internally as a JSON array (the final output wraps this in Step 5):

```json
[
  {
    "category": "correctness",
    "confidence": 0,
    "file": "src/db.py",
    "line_range": [10, 15],
    "description": "One-line description",
    "reasoning": "Why this is a real issue, be specific"
  }
]
```

Set `confidence` to your preliminary estimate; Step 4 will refine it.

For convention findings, also include `rule_quote` (exact text from convention file) and `rule_source` (convention file path). Omit both for all other categories.

`category` must be one of: `"correctness"`, `"security"`, `"convention"`, `"resource"`.

If no findings after reviewing all categories:
```json
[]
```

## Step 4 — Self-Review

Re-evaluate your findings list. This is a second pass over the findings only — do NOT re-read the full diff.

For each finding, re-evaluate the confidence you assigned (0-100). Apply the discard rules first — any match sets confidence to 0 and the finding is removed:

| Confidence | Meaning |
|---|---|
| 0 | False positive or pre-existing |
| 25 | Might be real, unverified |
| 50 | Real but minor/rare |
| 75 | Verified, important |
| 100 | Certain, frequent, confirmed |

**Remove (confidence 0) if ANY apply:**
- Pre-existing issue not introduced by the diff
- A linter, type checker, or CI would catch it
- Pedantic nitpick a senior dev would not flag
- Intentional change consistent with the diff's purpose
- Line has a suppression marker
- General quality concern without convention file backing
- Convention finding that cannot cite exact rule text from a convention file

For convention findings: verify the rule_quote is literally stated in the rule_source. If not → confidence 0.

**Deduplicate (per category — never across categories):**

1. Group all surviving findings by their category (correctness, security, convention, resource).
2. Within each group: if two findings target the same file AND their line ranges overlap (share at least one common line), keep only the one with the higher confidence. Discard the other.
3. Findings in different categories are NEVER duplicates of each other, even if they flag the exact same file and line. A security issue and a correctness bug on line 42 are two independent problems — both survive.

Example — three findings on `auth.py` line 42:
| # | Category | Confidence | Survives? |
|---|----------|------------|-----------|
| A | security | 90 | Yes |
| B | security | 75 | No — same category as A, same line, lower confidence |
| C | correctness | 80 | Yes — different category from A, never compared |

## Step 5 — Output

### Build JSON

Wrap surviving findings in `{"findings": [...]}`. Drop `rule_quote` and `rule_source` from convention findings.

Example:

```json
{
  "findings": [
    {
      "category": "security",
      "confidence": 95,
      "file": "src/db.py",
      "line_range": [42, 44],
      "description": "SQL injection via string concat",
      "reasoning": "User input interpolated directly into query"
    }
  ]
}
```

If nothing survives → `{"findings": []}`.

### Render Markdown

Pipe JSON to the render script via stdin. The script validates, filters by threshold, sorts by confidence descending, computes severity, and renders markdown.

```bash
echo '<json>' | uv run --with pydantic python3 scripts/render_markdown.py --threshold THRESHOLD
```

Replace THRESHOLD with the numeric value from Step 1 (default 75).

- If the script exits 0 → capture the markdown output
- If the script exits 1 → fix the JSON errors reported on stderr and retry

### Deliver

**Local / Branch mode:** print rendered markdown to stdout.

**PR mode:**

1. Re-eligibility check:
   ```bash
   gh pr view <number> --json state
   ```
   If CLOSED or MERGED → print markdown to terminal instead. Inform the user the PR was closed during review.

2. Enrich markdown with GitHub permalinks: for each line matching `**File:**`, insert the permalink URL on the next line:
   ```
   https://github.com/{owner}/{repo}/blob/{headRefOid}/{file}#L{start}-L{end}
   ```
   Use `headRefOid` saved from Step 2a. Extract `{owner}/{repo}` from the PR `url` field.

   Example — enriched detail section for PR mode:

   ```
   ### 1. SQL injection via string concat
   **File:** src/db.py (lines 42-44) · **security** · Confidence: 95
   https://github.com/owner/repo/blob/abc123def/src/db.py#L42-L44
   User input interpolated directly into query without parameterization.
   ```

3. Post enriched markdown via `gh pr comment <number> --body '...'`
   If `gh pr comment` exits with a non-zero status code, print markdown to terminal instead and display the gh error message. Do not retry.

**Clean review (no findings):** print clean markdown to stdout (local/branch) or post as PR comment (PR mode). No permalink enrichment.

## JSON Schema Reference

The render script validates against this schema:

```json
{
  "$defs": {
    "Finding": {
      "properties": {
        "category": {
          "enum": [
            "correctness",
            "security",
            "convention",
            "resource"
          ],
          "title": "Category",
          "type": "string"
        },
        "confidence": {
          "maximum": 100,
          "minimum": 0,
          "title": "Confidence",
          "type": "integer"
        },
        "file": {
          "minLength": 1,
          "title": "File",
          "type": "string"
        },
        "line_range": {
          "maxItems": 2,
          "minItems": 2,
          "prefixItems": [
            {
              "minimum": 1,
              "type": "integer"
            },
            {
              "minimum": 1,
              "type": "integer"
            }
          ],
          "title": "Line Range",
          "type": "array"
        },
        "description": {
          "minLength": 1,
          "title": "Description",
          "type": "string"
        },
        "reasoning": {
          "minLength": 1,
          "title": "Reasoning",
          "type": "string"
        }
      },
      "required": [
        "category",
        "confidence",
        "file",
        "line_range",
        "description",
        "reasoning"
      ],
      "title": "Finding",
      "type": "object"
    }
  },
  "properties": {
    "findings": {
      "items": {
        "$ref": "#/$defs/Finding"
      },
      "title": "Findings",
      "type": "array"
    }
  },
  "required": [
    "findings"
  ],
  "title": "ReviewOutput",
  "type": "object"
}
```

This schema describes the Step 5 output format. `severity` is computed by the script from `confidence` — do not include it.
